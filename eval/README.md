# 测评

衡量「模型抽取 + 规则判断」这套做法，和直接把公告交给大模型相比，哪个更少把本来能报的岗位错误排除。

## 怎么跑

需要先配置大模型（`LLM_PROVIDER`、`LLM_API_KEY`）。Windows 下双击仓库根目录的 `run-eval.cmd`，报告写到 `eval/reports/`。

## 比较什么

每份公告 × 每个虚构求职者，得出三个结论：

| | 做法 |
|---|---|
| 标准答案 | 人工写的条件（`gold`）→ 规则判断 |
| 本系统 | 模型抽取的条件 → 同一套规则判断（模拟用户对抽取结果全部点了确认） |
| 对照组 | 把公告和求职者情况直接交给同一个模型，问能不能报 |

指标：
- **错误排除**（核心）：标准答案为「符合」或「待核实」，却被判「不符合」。
- **错误放行**：标准答案为「不符合」，却被判「符合」。
- **确定率**：给出确定结论而非「待核实」的比例，防止靠全答「待核实」回避错误。
- 条件抽取：正确 / 参数错误 / 遗漏 / 多抽，引用在原文中找到的比例，数值核对报警数。

## 数据

| 位置 | 内容 | 是否进 Git |
|---|---|---|
| `profiles.json` | 虚构求职者 | 是 |
| `cases/` | 虚构样例公告，用来验证测评程序本身 | 是 |
| `private/` | 真实公告与人工核对的标准答案 | **否** |
| `reports/` | 测评报告 | **否** |

用例格式见 `cases/` 下的样例。`split` 字段区分用途：`dev` 可以用来调整提示词；`test` 在调试时不看，只在最后运行一次，用它得出的数字才算数。

## 注意

- 标准答案必须由人逐条核对。第一版样例里曾把「通过六级」写成只要持有六级成绩即可，漏掉了 425 分通过线，是跑测评时发现并修正的。
- 模型的输出不完全确定，同一份数据多跑几次，结果可能略有差异；已关闭 DeepSeek 的思考模式并设置 temperature=0 以减少波动。
- 样本量小时，结果只作诊断参考，不代表普遍可靠性。
