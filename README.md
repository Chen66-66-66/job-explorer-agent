# 校招岗位探索 Agent（job-explorer-agent）

人机协作的校招岗位探索工具：用户把招聘公告和岗位录入系统，大模型抽取报名条件，程序逐条判断能不能报。**每条结论附原文出处；拿不准的一律标「待核实」，宁可多问一句，也不错误排除岗位。**

> 已完成 M1（条件抽取与判断）和 M3（工具调用型 Agent），均已用真实模型（DeepSeek）跑通；测评（M2）进行中，见文末路线图。

## 为什么做这个

作者在秋招中用通用 AI 助手投递了十几家央国企，遇到三个反复出现的问题：

| 问题 | 表现 | 本项目的做法 |
|---|---|---|
| 长任务做不完 | 让 AI 统计全部岗位，几十轮对话仍未完成，每轮都要重读材料 | 「公司 → 岗位」分层：公司级条件不符合就整家剪掉；结果存入数据库，可中断续做 |
| 结论没有出处 | AI 摘要与公告原文不一致，事后难以核对 | 每条条件附原文引用，程序核对引用与其中的数值，再由人工确认 |
| 判断不可复现 | 同一问题不同时间问，答案可能不同 | 是否符合由确定性规则计算，大模型只负责读懂文字 |

## 工作流程

```
① 公司：录入公司与招聘公告 ──► 抽取公司级条件 ──► 任一不符合则整家剪掉
                                                   │
② 岗位：用户登录招聘网站，把感兴趣的岗位录入 ◄─────┘
                                                   │
③ 判断：公司级 + 岗位级条件逐条比对 ──► 符合 / 不符合 / 待核实（附原文）
                                                   │
④ 问 Agent：「我能报哪些？」模型自行调用只读工具查询判断结果，分组回答并附依据
                                                   │
⑤ 记录：投递状态与笔记存库，随时继续
```

## 核心设计

**1. 大模型只读，不判。** 模型从公告中抽取结构化条件（学历、英语、年龄、毕业时间窗口等）并给出原文引用；「是否符合」由 `EligibilityChecker` 用确定性规则计算，可复现、有单元测试。

**2. 程序核对 + 人工确认。** 程序能核对的做两项：引用是否逐字出现在原文中（`QuoteVerifier`）；解析出的分数、年龄、日期是否出现在引用里（例如原文 500 分却解析成 200 分会被发现）。程序核对不能保证模型理解正确，所以模型抽取的条件在**人工确认前一律只算「待核实」**。

**3. 分支条件。** 「本科不超过 25 周岁、硕士不超过 28 周岁」按适用对象分别判断，只看适用于本人的；「六级或雅思满足其一」作为一组，任一满足即可。适用对象无法自动识别时不据此排除。

**4. 谨慎剪枝。** 只有人工确认「适用于本批次全部岗位」的公司级条件，才能用来整家排除；否则只作提示。公告或 JD 还没核查完时，整体结论最多是「已核查部分通过」，不会显示「符合」。JD 改动后，原有核查自动失效。

**5. Agent 只读、只转述。** 「问 Agent」页面里，模型可以调用四个只读工具（列出公司、查看公司条件、列出岗位、查看岗位条件），自行决定查询顺序；它不能修改数据，也不能改判规则算出的结论。页面会列出每一次工具调用，没有调用工具的回答会被标为「没有依据」。

**6. 合规采集边界。** 需要登录的招聘网站由用户本人登录查看后录入；系统不绕过登录、验证码或加密接口。

**7. 个人信息只在本机。** 仓库里只有虚构的演示档案，真实档案放在 `backend/data/profile.local.yml`（已被 `.gitignore` 排除）；服务只监听 127.0.0.1；不提供读取完整档案的接口；条件抽取时只发送公告或 JD 原文，不发送个人档案。注意：使用「问 Agent」时，判断理由会发送给模型，其中可能包含由档案算出的年龄、证书分数等。

## 已知局限

- 引用核对只能证明「原文里有这句话」，不能证明模型对这句话理解正确，因此需要人工确认。
- 适用对象目前只能自动识别学历层次和境内 / 境外院校，其他分支条件交给人判断。
- 提示词中已声明不执行原文里的指令，但尚未系统测试提示词注入（计划在 M2 测评中覆盖）。

## 运行

需要 JDK 21+ 和 Node.js 20+，不需要单独安装数据库（使用内嵌 H2）。

```bash
# 后端（http://localhost:8080），Windows 可直接双击 start-backend.cmd
cd backend
./mvnw spring-boot:run

# 前端（http://localhost:5173），Windows 可直接双击 start-frontend.cmd
cd frontend
npm install
npm run dev
```

首次启动会写入四家**虚构**公司的演示数据，分别演示：整家被剪枝、条件基本符合、模型引用核对失败、分支条件。

**启用大模型抽取（可选）**：默认不启用，不影响其他功能，条件可以手动录入。使用 DeepSeek 时设置：

```bash
LLM_PROVIDER=deepseek
LLM_API_KEY=你的密钥
# 可选：LLM_MODEL（默认 deepseek-chat）、LLM_BASE_URL
```

**使用自己的档案**：复制 `backend/src/main/resources/profile-example.yml` 到 `backend/data/profile.local.yml` 后修改。

## 目录

```
backend/src/main/java/io/github/jobexplorer/
├─ domain/       公司、公告、岗位、条件、笔记
├─ agent/        AgentService（工具调用型 Agent）、JobTools（只读工具）
├─ service/      QuoteVerifier（引用核对）、EligibilityChecker（规则判断）、
│                LlmRequirementExtractor（模型抽取）、AssessmentService（分层判断）

├─ eval/         测评程序（与正式流程共用抽取和判断代码）
└─ demo/         虚构演示数据
frontend/src/
├─ views/        公司列表、公司详情、岗位详情、问 Agent
└─ components/   判断结果列表、条件录入表单
```

## 路线图

- [x] **M1 数据底座与判断**：公司 → 岗位树、公告与 JD 原文保存、真实模型条件抽取、引用与数值核对、分支条件、人工确认、规则判断、谨慎剪枝、笔记
- [ ] **M2 抽取测评**（测评程序已完成，见 [eval/](eval/README.md)；真实公告测评进行中）：用未参与调试的真实公告建立标准答案，重点统计**本可报名却被错误排除的岗位数**，以及漏掉的硬条件数、能给出确定结论的比例；包含提示词注入用例；与直接询问聊天模型（相同原文、档案与模型）对比
- [x] **M3 Agent：查询与判断**：针对已录入的公司和岗位，模型自行调用只读工具查询判断结果，回答「我能报哪些」并附依据与调用记录
- [ ] **M4 Agent：找公司与指路**：根据档案和公开信息建议候选公司，给出「去哪里、找什么岗位」的建议，每条标注依据或「推测」
- [ ] 暂缓：简历初稿生成、网申填写稿
